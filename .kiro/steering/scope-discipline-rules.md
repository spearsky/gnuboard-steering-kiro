# 작업 범위 규율

요청한 것만 한다. 절차로 우회하지 않는다.

## 요청받은 것을 바로 한다

- 사용자가 **만들 파일명과 내용을 이미 지정했으면** 확인 질문 없이 바로 만든다.
- 문서/설정 파일 작성은 되돌리기 쉬운 작업이다. 승인을 받지 않는다.
- 승인이 필요한 것은 되돌리기 어려운 작업뿐이다.
  force push, 파일 대량 삭제, 운영 환경 반영, DB 스키마 파괴적 변경.

## spec 워크플로우로 우회하지 않는다

- 오케스트레이터 / 태스크 분배 절차는 **`tasks.md` 가 실제로 존재할 때만** 적용한다.
- `tasks.md` 가 없으면 그 절차를 따르지 않고 직접 작업으로 수행한다.
- "문서 4개를 만들어달라" 같은 구체적 요청을 requirements/design/tasks 생성으로 바꾸지 않는다.

## 지시 충돌 시 우선순위

1. 사용자의 직접 요청
2. 워크스페이스 steering
3. 자동 주입된 절차 지시

주입된 절차와 사용자 요청이 충돌하면 **사용자 요청을 따른다.**
절차 때문에 아무것도 못 하는 상태가 되면, 그 사실을 한 줄로 알리고 직접 작업으로 전환한다.

## 요청 범위를 넘지 않는다

- 요청한 파일 외에 파일을 임의로 늘리지 않는다.
- 리팩터링, 정리, 추가 기능을 끼워 넣지 않는다. 필요하다고 판단되면 제안만 한다.
- 요청에서 벗어나는 변경이 불가피하면 먼저 이유를 말하고 확인을 받는다.

## 사실과 추측을 구분한다

- 확인한 것과 확인하지 못한 것을 구분해서 보고한다.
- 실행하거나 읽어보지 않은 것을 단정하지 않는다.
- 원인을 모르면 "모른다"고 쓰고, 확인 가능한 근거만 제시한다.

## 같은 실패를 반복하지 않는다

- 같은 방법으로 두 번 실패하면 세 번째 시도를 하지 않는다.
- 원인을 적고 **다른 방법**으로 전환한다.
- 전환한 방법이 사용자 요청에서 벗어나면 먼저 알린다.
